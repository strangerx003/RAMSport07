## 1. Architecture Overview

RAMSport is a **client-side single-page application** built with Next.js 16 (App Router) in static export mode. It follows a local-first architecture with all logic, data, and authentication running in the browser.

## 2. Architectural Principles

- **Static-First**: No server-side rendering, no API routes - fully static
- **Client-Side Only**: All computation in browser
- **Local-First**: Data owned by user in their browser
- **Account-Isolated**: Multi-user support on same device via localStorage namespacing
- **Separation of Concerns**: Clear layers (UI, logic, data, services)
- **Type-Safe**: Full TypeScript coverage

## 6. Key Design Decisions

| Decision | Rationale |
|---|---|
| Next.js static export | No backend needed, easy deployment to Vercel/Pages |
| localStorage | Simple, no DB setup, works offline |
| PBKDF2 in browser | Better than plain text, acceptable for local app |
| Account isolation | Support multiple users on same machine |
| Modular RBD engine | Extracted for maintainability/testability |
| Client-side exports | No server processing needed |
| Route groups | Clean organization of auth vs public routes |

## 7. Security Considerations

### Current (Local-First)
- **Password hashing**: PBKDF2-SHA-256 with 310000 iterations ?
- **No plain text passwords**: Only hashes stored ?
- **Timing-safe comparison**: XOR-based comparison in `equalHashes()` ?
- **Account isolation**: Keys namespaced by account ?
- **Built-in accounts protected**: Cannot remove admin/test ?
- **Client-side only**: No network exposure of auth logic

### Limitations
- **localStorage accessible**: Any JS on page can read (XSS risk)
- **No CSRF protection needed** (no server)
- **No rate limiting** (client-side only)
- **Passwords in memory** during auth
- **Not production-ready** for multi-tenant cloud use

**Note:** README states "This is a client-side app with localStorage auth - for production use, move authentication to a secure server-side backend."

## 8. Performance Considerations

- **Static assets**: Pre-rendered, fast load
- **Code splitting**: Next.js automatic
- **Client-side only**: No server latency
- **localStorage**: Synchronous but small data
- **Canvas rendering**: DOM-based, may need optimization for large diagrams
- **Calculations**: Pure JS, fast enough

## 10. Build & Deployment Architecture

### Build Process
```bash
npm run build  # next build with output: 'export'
# Outputs to out/ directory
```

### Deployment Targets
- **Vercel**: Auto-deploy from git, serves static files
- **GitHub Pages**: Via `build:pages` script
- **Static hosting**: Any CDN/static server
- **Local**: Via `win.bat`, `run.sh`, or the static preview server

### Configuration
- `next.config.ts`: Static export enabled
- `vercel.json`: Vercel-specific config
- `tsconfig.json`: Path aliases, strict mode

## 14. Conclusion

RAMSport follows a clean, maintainable architecture appropriate for a local-first engineering tool. The static export architecture enables simple deployment without backend infrastructure.
